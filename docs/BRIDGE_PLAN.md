# 双进程融合方案

## 目标

同时运行 Stardew Valley 和 Terraria，让两个游戏通过本机 localhost 通信。第一阶段采用“窗口接力”而不是把一个游戏的画面注入另一个游戏：玩家在 Stardew 的传送门处进入 Terraria，桥接器保存并同步必要状态，然后把焦点交给 Terraria；返回时反向执行。

## 三种实现层级

### A. 当前方案：原生内容移植

只有 Stardew 进程运行。Terraria 的武器、怪物和矿洞规则在 SMAPI 中重写。

### B. 推荐的第一版双进程方案：事件桥 + 窗口接力

两个游戏都运行，但每个游戏继续使用自己的渲染器、物理和存档。桥接器只同步：

- 传送门进入/返回；
- 玩家身份、生命、货币和有限的物品映射；
- 游戏内日期、时间、天气和世界种子标签；
- 击杀、掉落、Boss 完成等离散事件；
- 心跳、加载、暂停、崩溃和重启状态。

这是第一版应实现的路线，因为它不需要反向工程两个渲染器，也不要求实时复制地形碰撞。

### C. 完整同屏融合：帧合成或原生几何桥

Terraria 的画面、深度和相机姿态要传给 Stardew，再由 Stardew 的渲染路径合成；或者由 Stardew 直接绘制 Terraria 的几何体。这个层级才是“Terraria 画面出现在 Stardew 世界里”，但需要平台相关的图形 hook、相机矩阵、深度处理、输入抢占和延迟校正。

## 双进程第一阶段的推荐职责

| 系统 | Stardew | Terraria |
|---|---|---|
| 农场、村庄、日程 | 拥有 | 不读取 |
| Terraria 世界、地形、敌人 AI | 不拥有 | 拥有 |
| 当前玩家输入 | 当前获得焦点的游戏 | 当前获得焦点的游戏 |
| 跨游戏进度 | 桥接器持有映射 | 桥接器持有映射 |
| 各自存档 | 各自拥有 | 各自拥有 |

第一版不连续同步两张地图的坐标，也不尝试让一个游戏的碰撞体直接成为另一个游戏的碰撞体。传送门是明确的状态边界，能避免两个游戏同时模拟同一个玩家。

## 启动顺序

1. 启动本地桥接器，监听 `127.0.0.1:28741`（可用 `SDTV_BRIDGE_PORT` 改变）。
2. 桥接器同时启动 SMAPI Stardew 进程和 tModLoader Terraria 进程；也可以用 `--no-launch`，先由用户分别启动两个已配置好的进程。
3. 两个端插件连接桥接器并完成握手。
4. 两端交换协议版本、游戏版本、存档 ID 和一个心跳。
5. 只有握手成功后，传送门才可用。

## 当前方案和单进程移植的取舍

| 方案 | 真实运行的进程 | 优点 | 成本和限制 |
|---|---|---|---|
| 单进程内容移植 | 只有 Stardew | 资源占用低，输入、渲染、存档和崩溃边界简单 | Terraria 的世界、AI、物理和原生 Mod 需要在 Stardew 中重写，不能直接得到 Terraria 的真实行为 |
| 当前双进程窗口接力 | Stardew + Terraria | 保留两边原生世界、NPC AI、物理和 Mod；跨游戏事件容易逐步增加 | 需要两个 loader 和两份存档；占用更多 CPU/RAM/GPU；焦点切换有延迟，两个窗口不是同一画面 |
| 双进程同屏合成（后续） | Stardew + Terraria | 可以让 Terraria 画面出现在 Stardew 场景中，视觉融合最强 | 需要图形 API hook、颜色/深度帧传输、相机和输入同步，平台和版本耦合明显，调试成本最高 |

因此，当前代码选择双进程窗口接力作为可验证的第一阶段：两个游戏确实同时运行，但同一时刻只有获得焦点的窗口接收主要输入。它为后续同屏合成保留了两个真实模拟器，同时避免一开始就把渲染器和碰撞系统绑在一起。

## macOS 约束

当前 Stardew 是原生 macOS x64 .NET/MonoGame。工作区 Terraria app bundle 同时包含原生 macOS x86_64/arm64 启动器和较旧 Windows PE32 程序集；`Terraria/changelog.txt` 标明游戏数据为 1.4.5.8。当前应优先使用原生启动器，不需要先引入 Wine/CrossOver。仍需安装与该游戏版本兼容的 tModLoader，才能加载 Terraria 端桥接 Mod。
